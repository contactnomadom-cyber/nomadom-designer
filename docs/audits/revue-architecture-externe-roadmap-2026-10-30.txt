NOMAD’OM DESIGNER

Analyse technique
et roadmap d’évolution

Audit de la version bêta 0.9.11

  -----------------------------------------------------------------------
  OBJECTIF
  Structurer l’évolution de Nomad’Om Designer sans réécriture globale :
  sécuriser l’existant, fiabiliser les calculs et préparer une
  architecture multi-produits.
  -----------------------------------------------------------------------

  -----------------------------------------------------------------------

1. Synthèse exécutive

Le principal enjeu n’est pas le fait que l’application soit distribuée
dans un fichier HTML unique. Ce format peut rester pratique pour la
livraison. L’enjeu est plutôt de maîtriser l’organisation du code
source, les dépendances entre modules, la validation des calculs et la
reproductibilité des versions.

La stratégie recommandée consiste à sécuriser l’existant, mettre en
place une chaîne de construction reproductible, renforcer les tests et
stabiliser les données métier avant d’étendre l’application à de
nouvelles familles de produits.

2. Les cinq enjeux prioritaires

1.  Architecture — Réduire progressivement la dépendance au script
    principal sans réécrire l’application.

2.  Fiabilité — S’assurer que toute modification pertinente invalide les
    calculs, statuts et résultats qui en dépendent.

3.  Données — Définir des structures de données stables pour la
    géométrie, le textile, les pièces de fabrication et les projets.

4.  Validation — Vérifier les résultats à l’aide de tests
    reproductibles, notamment sur deux dômes de référence.

5.  Évolutivité — Créer un noyau commun permettant d’ajouter des
    familles de produits sans mélanger leurs règles métier.

3. Architecture cible

L’architecture cible peut être organisée en six couches aux
responsabilités explicites.

  -----------------------------------------------------------------------
  Couche                              Responsabilité
  ----------------------------------- -----------------------------------
  1. Géométrie                        Sphères, dômes, fréquences,
                                      sommets, barres, faces et
                                      ouvertures structurelles.

  2. Textile                          Paramètres de toile, patrons,
                                      découpes et propriétés des pièces
                                      textiles.

  3. Fabrication                      Développés, assemblages, nesting,
                                      optimisation et contrôles de
                                      fabrication.

  4. Produits                         Règles spécifiques aux habitats,
                                      Quadrisphères, objets décoratifs et
                                      Kumiko.

  5. Application                      État du projet, orchestration,
                                      sauvegarde, importation et
                                      exportation.

  6. Présentation                     Interface, visualisation 2D/3D et
                                      retours utilisateur.
  -----------------------------------------------------------------------

[CODE] Le fichier comporte notamment geometryStatus(),

window.CoverApp. [RECOMMANDATION] Ces responsabilités devraient être
isolées progressivement, en conservant les comportements existants et en
extrayant les modules par étapes.

4. Roadmap priorisée

Phase 1 — Sécuriser l’existant

Priorité critique

-   Mettre le projet sous Git et définir une version de référence.

-   Organiser les sources JavaScript en fichiers distincts.

-   Créer un script d’assemblage automatique du HTML final.

-   Vérifier que le fichier assemblé reproduit les comportements de la
    version actuelle.

Livrable : projet versionné, reproductible et toujours distribuable sous
la forme d’un seul HTML.

Phase 2 — Fiabiliser calculs et statuts

Priorité critique

-   Cartographier les dépendances entre géométrie, textile, fabrication
    et affichage.

-   Définir les règles d’invalidation après chaque modification.

-   Distinguer les résultats à jour des résultats périmés.

-   Clarifier les conditions de validation et de blocage des exports.

-   Tester les cas acceptés, refusés et incomplets.

Livrable : validation cohérente qui ne présente pas un résultat périmé
comme valide.

Phase 3 — Stabiliser les données métier

Priorité élevée

-   Définir DomeGeometry pour la définition et les résultats
    géométriques.

-   Définir FabricSpec pour les paramètres textiles.

-   Définir FabricPiece pour une pièce textile à fabriquer.

-   Définir Project pour le projet et ses paramètres.

-   Définir FabricationResult pour les résultats et preuves de
    validation.

-   Distinguer le patron théorique d’une pièce de sa disposition sur une
    feuille de matière.

Livrable : contrats de données stables entre les modules.

Phase 4 — Construire une base de tests

Priorité élevée

-   Créer des jeux de référence pour les deux dômes existants.

-   Tester les résultats géométriques et les ouvertures.

-   Tester les paramètres textiles et les invalidations.

-   Tester les statuts, imports, exports et sauvegardes.

-   Tester le HTML final assemblé.

Livrable : suite de régression capable de détecter les erreurs avant
publication.

Phase 5 — Extraire progressivement les modules

Priorité élevée

-   Isoler la logique de statut.

-   Séparer l’orchestration de l’application.

-   Clarifier les responsabilités de la géométrie et de la fabrication.

-   Séparer la logique métier du rendu 3D.

-   Réduire progressivement les dépendances globales.

Livrable : architecture modulaire sans rupture fonctionnelle.

Phase 6 — Préparer les familles de produits

Priorité moyenne à élevée

-   Définir le noyau commun et ses limites.

-   Créer des modules spécifiques pour les habitats géodésiques,
    Quadrisphères événementielles, objets décoratifs, structures Kumiko
    et Nomad Vision.

-   Réutiliser les composants communs uniquement lorsque leurs règles
    sont réellement partagées.

Livrable : plateforme extensible, avec socle commun et logiques produit
indépendantes.

Phase 7 — Renforcer la gestion des projets

Priorité moyenne

-   Versionner le format JSON des projets.

-   Valider les données importées et contrôler les fichiers GLB et
    ressources associées.

-   Prévoir une stratégie de migration des anciens projets.

-   Distinguer les préférences locales des données de projet à
    conserver.

Livrable : projets portables, récupérables et compatibles avec les
évolutions futures.

6. Principes à préserver

-   Ne pas lancer de réécriture globale avant d’avoir sécurisé
    l’existant.

-   Ne pas ajouter une famille de produits sans définir ses données et
    ses responsabilités.

-   Ne pas déclarer un résultat de fabrication valide sans contrôles
    explicites.

-   Ne pas réaliser de modification structurelle majeure sans tests de
    régression.

-   Éviter les dépendances implicites entre modules : chaque échange
    important doit être identifiable.

-   Générer le HTML final de manière reproductible plutôt que de
    maintenir manuellement une version assemblée fragile.

7. Recommandation finale

Concentrer le premier chantier sur trois objectifs :

6.  Maîtriser le code — Git, organisation des sources et assemblage
    automatique.

7.  Maîtriser la fiabilité — Tests de référence, invalidation des
    calculs et statuts de validation.

8.  Maîtriser les données — Objets métier stables et séparation entre
    géométrie, textile et fabrication.

Conclusion

L’objectif n’est pas de rendre le code plus abstrait ou plus complexe.
Il est de rendre chaque évolution plus prévisible, chaque résultat plus
fiable et chaque nouveau produit moins coûteux à développer. La priorité
est donc de consolider l’architecture et le processus de validation
avant d’élargir fortement le périmètre fonctionnel.
